# MAIL-135: **A mail folder held back for being in iCloud Drive or a File Provider folder is opened read-only**

**Decision.** **While `AccountSync.folderHold` is set (MAIL-126), the store is opened read-only and nothing is written into the mail folder, by any path.** `AppModel.open()` asks the placement first and passes the held notice's words to `MailStore.open(_:readOnlyReason:)`. A read-only store never creates the folder, writes `layout.json`, recovers an interrupted write or rebuilds the index (a rebuild reads every original, which downloads the ones a File Provider evicted); `recoveryDeferred` says when one of those was due, so the list may be incomplete until the folder is moved. Every writer of the folder asks one gate, `MailStore.requireWritable()`, and throws `MailStoreError.readOnly(reason)` (new mail, an account's `account.json`, removing or disconnecting an account, space files, removing mail deleted at the provider, rebuilding); drafts are the same through `DraftStore(readOnlyReason:)`, which also does not adopt a sync tool's conflict files. The index and the device state are outside the folder (MAIL-013) and stay writable. The outbox pauses: it lists what is queued, but nothing is sent, retried, checked or cancelled (`MailSending.readOnlyReason`, no background pump), since sending deletes the draft from the folder and its sent copy follows. In the app model the question is `AppModel.writeRefusal` (`canWrite`, `refuseWrite()`, and `MenuCommand.writesMailFolder` in `unavailableReason`): New Message, Reply, Reply All, Forward, Import Messages…, Add Account…, New Space…, Rebuild Search Index and removing an account are refused or disabled, and say "Your mail folder is in iCloud Drive, where Mail can’t write safely yet, so it is read-only and this can’t be done. Move the folder out of iCloud Drive in the Finder and choose it again in Settings ▸ Storage, or use the default mail folder." (`MailFolderPlacement.readOnlyText`); the sidebar notice and Settings ▸ Storage say the folder is read-only as well as paused. Space rules are not applied while read-only (that would write), which is not an error.

**Why.** MAIL-126 held only the sync, so a held folder still took writes without `NSFileCoordinator` from opening, drafts, import, spaces and account edits. One gate in the store, rather than a check in each view, means a new writer that asks it is safe by default, and one that forgets still meets the check in the app model's intents; the views only disable what would be refused. Skipping recovery and rebuild on open is the safe half of "decide what opening does": they would write (and download) exactly where the hold says not to, and the folder is read-only until the person moves it, after which the next writable open does them. Marks and moves of mail (read, archive, junk) are device state (the index and the action journal) and are not refused; they wait in the journal because the sync is held. `Tests/HeldFolderReadOnlyTests.swift` (a snapshot of every file and folder with sizes and modification times is identical after open, browse, a draft, an import, a space edit, account changes, a rebuild and an outbox attempt; a normal folder still writes and tidies up) and `ReadOnlyStoreTests` (the store alone).
