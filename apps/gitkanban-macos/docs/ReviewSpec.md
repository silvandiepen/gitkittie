# Review as a first-class feature: spec

Status: **proposal** (GITKITTIE-129). Nothing here is built yet. The open decisions are asked as a
review on the board: `GitKittie/review/GITKITTIE-129-review-first-class/`. Each one has a
recommended answer below; this document follows the recommendations, and § 9 lists what each other
answer would change.

Sil's brief: when a review is accepted, a linked card goes to another lane, set in the review.
Good support for checking something in a browser: a checklist, per size, opened at that size.
Reviews that work with several people: a review can be put on someone's name, and other people
don't see it.

This spec covers four parts:

1. **Actions on decision**: what happens to cards when a request (or one item) is accepted, gets
   changes requested, or is rejected.
2. **Browser checks**: a new kind of entry, "check this page in a browser", with sizes, a
   checklist answered per size, and screenshots.
3. **Assigning reviews**: a request for one or more board users, seen by them and announced only
   to them.
4. **Other gaps**, in priority order, and what goes in the first release.

Related work in flight, which this spec builds on and does not repeat:

- `feat/tasks-review-push` (GITKITTIE-128): `notify: urgent | normal | silent` on a request and the
  relay that pushes new requests to devices. Assignment (§ 4) narrows who that push goes to.
- `feat/tasks-review-viewer`: the iOS full-screen viewer, **Changes needs a comment**
  (`ReviewDecisionRule`), reused comments, waiting markers. Actions (§ 2) reuse that comment as the
  card's feedback.

## 1. Where the contract lives today, and where it should

What I found:

| Text | Where | Shipped by Tasks? |
|---|---|---|
| The `review.md` schema, field ownership, workflow | `project-assets/Agents/review-workflow.md` (Sil's conventions folder) | No. Hand-written. |
| `review_path` (where requests live) | `tasks/README.md` § Board configuration | No. The board repo's own README. `get_board_rules` returns it as the `contract`. |
| How agents ask and read back | `swift/GitKanbanKit/Sources/TasksAgentTools/AgentGuide.md` § 6 | **Yes**: prose in the app, returned by `tasks guide` and `get_agent_guide`; the references are generated from `AgentTools.all` and `CommandTable`. |
| The parser and writer | `packages/gitkanban-core/src/review.ts` (source of truth), mirrored in `swift/GitKittieKit/.../Review.swift` | Yes, as code. |

So the board's README is **not** generated by Tasks and does not hold the review schema; it only
names `review_path`. The schema is written down in two hand-maintained places
(`review-workflow.md`, `AgentGuide.md`) plus the code.

**Proposal:** the review schema's source of truth is `gitkanban-core` + `AgentGuide.md`, because
they ship with the app that parses the file: a field an agent reads about is a field this app
version understands. The board README gets a short **Reviews** section that points there (diff in
§ 7.1), and `review-workflow.md` keeps the workflow (when to ask, what to do with answers) and
points at the guide for the field list (diff in § 7.2). Neither file is edited by this PR: the
board repo is shared by agents and `project-assets` is Sil's.

## 2. Actions on decision

### 2.1 What it is

A request declares what happens to cards when it is decided. The usual case is the request's own
card: accepted → Testing, changes → back to In Progress with the feedback on the card.

```yaml
card: GITKITTIE-131
on_accept:  { to: testing }                         # move: defaults to the request's `card`
on_changes: { to: in-progress, comment: true }
on_reject:  { to: todo, comment: true }
```

An item (or a check, § 3) can carry its own actions, for a request that reviews several cards'
work at once (one screenshot per card):

```yaml
items:
  - id: badge-sync
    file: badge-sync.png
    on_accept:  { move: GITKITTIE-140, to: testing }
    on_changes: { move: GITKITTIE-140, to: in-progress, comment: true }
```

### 2.2 Fields

`on_accept`, `on_changes`, `on_reject`: one action, or a list of actions. Written by the agent.

| Key | Meaning | Default |
|---|---|---|
| `move` | Card id on the same board. | The request's `card` (request level); required on an item. |
| `to` | Lane: id, status or name, resolved like `move_card` does (`AgentBoard.lane`). | Required. |
| `comment` | Copy the reviewer's comments on what was decided into the card's activity log. | `false` |
| `assign` | Set the card's `assignee` to this board user (e.g. back to the agent on changes). | unchanged |

The request-level `on_accept` / `on_changes` also fill the card's own review fields from the board
contract: `reviewer` (the reviewer's board id), `review_outcome` (`approved` /
`changes-requested`), `review_completed_at`. `on_reject` leaves them alone (rejected is "drop
this", not a review outcome the contract knows). *(Question `review-fields`.)*

### 2.3 When it runs

- **Item and check actions** run when that entry is decided.
- **Request actions** run when the request has an **outcome**, which is when every item and check
  is settled. An entry is settled when it is decided, or when it is a not-approved option of a
  pick-one group that has an approved option (losers of a pick may stay pending). Questions don't
  count: they have answers, not decisions. A request with only questions has no outcome and its
  actions never run (create_review refuses `on_*` on such a request).
- **Outcome rule** *(question `outcome`)*:
  - any `changes-requested` → **changes**;
  - else any `rejected` (pick-one losers excluded) → **reject**;
  - else → **accept**.
- **Automatically, with Undo** *(question `when`)*: the decision that completes the request also
  runs the action. The screen shows a banner: "Accepted · GITKITTIE-131 moved to Testing · Undo".
  No extra button: the decision is the confirmation, and the banner says exactly what happened.
- **Once per outcome.** A decision changed afterwards (allowed until the agent handles it) that
  flips the outcome does not undo or re-run anything by itself; the banner offers the new outcome's
  action ("Now: changes · Move GITKITTIE-131 to In Progress?"). Moving cards back and forth on
  every tap would spam the card's history.

### 2.4 Who performs it

The app on the reviewer's device, right after the review write, through **the agent write path**
(`AgentBoard.updateCard`), not `AppModel.moveCard`:

- it resolves and validates the lane against the effective board config (lanes are folders, a
  card's `status` follows its lane: README "Board configuration");
- it writes with `AgentCardText`, which keeps unknown frontmatter keys (`CardText.update` quotes
  values and cannot write `null`);
- it appends the activity entry and sets `updated_at`.

The review write and the card write are two writes. Where the provider can commit several files at
once (`provider.capabilities.contains(.batchCommit)`, through GitPont) they go as one commit. Offline,
the action is queued in the outbox **after** the review edit as its own entry
(`ReviewEdit.action(...)`), and re-validated when sent (§ 2.6).

Commit message: `chore(tasks): move GITKITTIE-131 to testing (review accepted)`.

### 2.5 Audit trail

On the card, one activity line per action, under the reviewer's board id:

```
- 2026-11-30T10:12:04Z — `sil` accepted review GITKITTIE-131-site-onboarding; moved to Testing.
- 2026-11-30T10:12:04Z — `sil` asked for changes in review GITKITTIE-131-site-onboarding; moved to In Progress. Feedback: "Download button is below the fold on phone (390×844)."
```

With `comment: true` the feedback is the comments written with the deciding decisions, each
quoted, at most 500 characters per entry with "(more in the review)" after a cut.

In `review.md`, the app appends to a top-level `actions_run` list (a reviewer field, append-only
like `comments`), so the agent sees what already happened and does not move the card again:

```yaml
actions_run:
  - on: changes              # accept | changes | reject
    entry: null              # null for the request; an item or check id otherwise
    card: GITKITTIE-131
    from: in-review
    to: in-progress
    result: moved            # moved | already | skipped | undone
    reason: null             # why it was skipped
    by: sil
    at: 2026-11-30T10:12:04Z
    undone_at: null
```

`list_reviews` returns `actions_run`; the agent guide says: if a review action moved your card,
don't move it again, act on the feedback.

### 2.6 Conflicts and validation

At **create time** (`create_review`): the card exists on this board, `to` resolves to a lane of the
board's effective config, `move` is a card on this board (no cross-board moves), and `assign` is a
board user. Refused with a message otherwise; nothing is written.

At **run time**, checked again on the file as it is now:

| Situation | What happens |
|---|---|
| Card is already in `to` | `result: already`, no write. |
| Card is in a terminal lane (`terminal: true`, Done) | Skipped; banner "GITKITTIE-131 is already Done. Move anyway?" |
| Card has an unexpired claim by someone other than the request's `requested_by` | Skipped; banner "GITKITTIE-131 is claimed by herma until 14:00. Move anyway?" *(question `conflict`)* |
| Card not found, or `to` no longer a lane | Skipped with the reason; the request shows it in red. |
| Claimed by `requested_by` (the usual case) | Moves. Claim fields are never touched by an action. |

"Move anyway" runs the same write with the check overridden and records it in the activity line
("moved to Testing although claimed by herma").

### 2.7 Undo

- The banner's Undo (8 seconds; ⌘Z on the Mac while the banner shows).
- Afterwards, the request's **Actions** section lists each `actions_run` entry with Undo, available
  while the card is still in `to` and its `updated_at` is the one the action wrote (nobody touched
  it since).
- Undo moves the card back to `from`, restores `assignee` and the review fields it changed,
  appends "undid the review action" to the activity log, and sets `undone_at`. It does not change
  the decision itself.

### 2.8 Tools and CLI

`create_review` gains `on_accept`, `on_changes`, `on_reject` (request level, and on each item and
check), each `{move?, to, comment?, assign?}` or a list of them.

`list_reviews` returns them, plus `outcome` (`accept` / `changes` / `reject` / `null`) and
`actions_run`.

The CLI gets a real create command (today it needs `tasks raw create_review` because files are
base64; requests without files don't, and the CLI can read files itself):

```sh
tasks review create --card GITKITTIE-131 --title "Site onboarding, round 1" \
  --question "Check the new onboarding page." \
  --on-accept testing --on-changes in-progress --comment-on-changes \
  --for sil --notify normal \
  --file after-phone.png --file after-desktop.png
```

| Option | Meaning |
|---|---|
| `--on-accept <lane>` / `--on-changes <lane>` / `--on-reject <lane>` | Request-level move of `--card`. |
| `--comment-on-changes`, `--comment-on-reject` | `comment: true` on that action. |
| `--assign-on-changes <user>` | `assign` on the changes action. |
| `--file <path>` (repeatable) | An item; kind from the extension; id from the file name. |
| `--for <user>` (repeatable) | § 4. |
| `--notify <level>` | From GITKITTIE-128. |
| `--due <YYYY-MM-DD>` | § 5. |
| `--request <id>` | Add to an existing request instead of `--title` (a redo). |

Anything richer (per-item actions, groups, questions) stays `tasks raw create_review`.

## 3. Browser checks

### 3.1 What it is

A new kind of entry: "open this page and check these things, at these sizes." Each statement on
the checklist is answered **pass**, **fail** or with a note, **per size**, and each size can get a
screenshot taken from the web view. The check as a whole is then decided like a file: Approve,
Changes or Reject. Its decision counts toward the request's outcome (§ 2.3).

### 3.2 Schema

Checks are a new top-level list, `checks:`, next to `items:` and `questions:`. Not items with
`kind: browser`: both parsers drop an item without `file` (`parseItem` returns `nil`), and a check
has no file.

```yaml
checks:
  - id: onboarding-page                 # unique across items, questions and checks
    url: https://preview-95.gitkittie.app/tasks/onboarding
    title: Onboarding page on the new site
    note: "Preview of PR #95. Compare with the design in docs/Onboarding.md."
    sizes: [phone, tablet, desktop]     # presets (§ 3.3) or custom mappings
    appearance: [light, dark]           # optional; each size is then checked in each
    checklist:
      - id: hero
        text: The headline fits without an awkward break
      - id: cta
        text: The download button shows without scrolling
      - id: contrast
        text: Text is readable on the background
    revises: null                       # a redo of an earlier check, like items
    on_accept: { move: GITKITTIE-131, to: testing }

    # Written by the app (the reviewer):
    results:
      phone.light:                      # <size id> or <size id>.<appearance>
        viewport: 390x844               # what was actually used (the phone's own size may differ)
        by: sil
        at: 2026-11-30T10:05:12Z
        screenshot: results/onboarding-page-phone.light.png
        answers:
          hero: { result: pass, at: 2026-11-30T10:04:40Z }
          cta: { result: fail, note: "Below the fold; the cookie bar pushes it down.", at: 2026-11-30T10:04:58Z }
          contrast: { result: pass, at: 2026-11-30T10:05:01Z }
    status: changes-requested           # pending | approved | rejected | changes-requested
    decided_by: sil
    decided_at: 2026-11-30T10:06:00Z
    comments:
      - { by: sil, at: 2026-11-30T10:06:00Z, text: "Phone: download button below the fold." }

    # Written by the agent:
    handled_at: null
```

Rules:

- `result` is `pass`, `fail` or `note` (only a note, no verdict: "looks off, not sure"). A `fail`
  may carry a note; a `note` must.
- Every answer carries its own `at`, so `ReviewEdits` can merge answers from two devices answer by
  answer, the same rule as decisions and comments.
- Screenshots go in `results/` inside the request folder, named `<check>-<size key>.png`. A newer
  screenshot of the same size replaces the file; git keeps the old one.
- Without `sizes` the check has one size, `default`: whatever window or screen it is opened in.

### 3.3 Size presets

Generic names, so they don't age with device models. Defined in `gitkanban-core` and listed in the
guide.

| id | CSS px | User agent |
|---|---|---|
| `phone-small` | 375 × 667 | mobile |
| `phone` | 390 × 844 | mobile |
| `phone-large` | 440 × 956 | mobile |
| `tablet` | 820 × 1180 | mobile (iPad) |
| `tablet-landscape` | 1180 × 820 | mobile (iPad) |
| `laptop` | 1280 × 800 | desktop |
| `desktop` | 1440 × 900 | desktop |
| `wide` | 1920 × 1080 | desktop |

A custom size is a mapping: `{ id: kiosk, label: Kiosk, width: 1080, height: 1920, ua: desktop }`
(`ua`: `mobile` | `desktop` | `default`).

### 3.4 Mac

In the review screen a check shows as a row with the URL, the sizes as chips with progress
("phone 3/3 · tablet 1/3 · desktop –"), the latest screenshots as thumbnails, and **Check in
Browser**.

**Check in Browser** opens a separate window (a `WindowGroup` keyed by the check), so the review
stays visible next to it:

- **Toolbar:** size picker (segmented: the check's sizes, then Custom), appearance toggle when the
  check lists both, back / forward / reload, the address (read-only, select to copy), and an
  **Open in Browser** menu.
- **Content:** a `WKWebView` whose frame is exactly the chosen viewport in CSS pixels at 100 %. The
  window's content size is locked to it; picking another size resizes the window. When the
  viewport doesn't fit the screen (956 px tall on a 13" display), the web view keeps its exact
  layout size and is shown scaled to fit, labelled "75 %". Layout is always computed at the real
  width, only the drawing is smaller. *Spike first:* scaling the hosting view's bounds keeps
  hit-testing right; check it in the first card.
- **Custom:** the window becomes freely resizable and the picker shows the live size
  ("1012 × 768"). Custom results are stored under `custom` with that viewport.
- **User agent:** `ua: mobile` sets an iPhone / iPad Safari user agent (`customUserAgent`), so a
  site that sniffs it serves its mobile layout.
- **Inspector (trailing):** the checklist for the current size. Each line: the statement, Pass /
  Fail buttons, and a note field that opens on Fail or on N. Under it: **Take Screenshot** (the
  visible viewport via `WKWebView.takeSnapshot`, at the window's backing scale), the size's
  screenshot thumbnail, and **Next Size**. At the bottom, the check's decision: Approve / Changes /
  Reject, with Changes pre-filled with the failed lines ("phone: Download button shows without
  scrolling — Below the fold; the cookie bar pushes it down.") and editable, since Changes needs a
  comment.
- **Keyboard:** ⌘1…⌘8 choose a size; ↑ / ↓ move between lines; P pass, F fail, N note; ⇧⌘S
  screenshot; ⌘] next size; ⌘R reload; ⌘↩ approve the check, ⌥⌘↩ ask for changes (same keys as
  the review screen's decision buttons).
- **Writes:** each answer is a review edit, written and queued like a decision (debounced a second
  so ticking through a list is one write). The screenshot is written to `results/` with the answer.

**Open in my browser at this size** *(question `browser-sizing`)*. Recommended: the in-app view is
the check, and **Open in Browser** opens the URL in the default browser with no sizing, with "Size
the window to 390 × 844" shown next to it. Sizing another browser's window needs AppleScript:

- Safari: `make new document with properties {URL: …}` then `set bounds of front window`. Bounds
  include the toolbar, so the viewport comes out smaller unless the app measures the browser's
  chrome first, and measuring needs `do JavaScript`, which only works when the user turns on
  Develop → Allow JavaScript from Apple Events.
- Chrome: the same with `execute javascript`, behind the same kind of setting. Command-line flags
  (`--window-size`, `--app`) only work when Chrome is not running yet.
- Firefox: no usable scripting for window bounds.
- Permissions: the sandboxed app needs `com.apple.security.automation.apple-events` and a
  temporary-exception entitlement naming each browser (Safari and Chrome publish no scripting
  access groups), plus the user's Automation consent per browser. Temporary exceptions are an App
  Store review risk.

So: not in the first release. If it is wanted later, behind a setting, Safari and Chrome only, and
the result stays "approximately this size".

### 3.5 iPhone and iPad

- The check row: URL, size chips with progress, thumbnails, **Check**.
- **Check** opens a full-screen `WKWebView` (not `SFSafariViewController`: that can't take a
  screenshot or set a user agent). The checklist is a sheet over it (medium / large detents),
  with Pass / Fail / Note per line, **Screenshot** and **Next Size**.
- **Sizes:** the device's own width is the natural size. The phone always offers its own viewport
  for the preset nearest to it and records the real one (`viewport: 402x874`). Larger sizes
  *(question `phone-sizes`)*: recommended, shown at their exact layout width scaled down to fit,
  labelled "Scaled preview" in the sheet, and allowed to be answered. That's enough to check
  layout, not small text. An iPad shows `tablet` natively.
- **⋯ menu:** Open in Safari (nothing is written back from Safari; the checklist stays answerable
  when you come back), Copy Link, Reload.
- **Unreachable addresses:** `localhost`, `127.0.0.1` and `*.local` only work on the machine that
  serves them. The row says so ("Only reachable on the Mac that made it") instead of opening a
  blank page. The guide tells agents to give a preview URL or a tailnet address.
- Plain `http://` addresses on a tailnet need `NSAllowsArbitraryLoadsInWebContent` in both apps'
  `project.yml` Info properties (web content only, not the app's own requests).

### 3.6 Agents

`create_review` gains `checks`:

```json
{
  "card": "GITKITTIE-131",
  "title": "Site onboarding, round 1",
  "for": ["sil"],
  "on_accept": {"to": "testing"},
  "on_changes": {"to": "in-progress", "comment": true},
  "checks": [{
    "id": "onboarding-page",
    "url": "https://preview-95.gitkittie.app/tasks/onboarding",
    "title": "Onboarding page on the new site",
    "sizes": ["phone", "desktop", {"id": "kiosk", "width": 1080, "height": 1920}],
    "appearance": ["light", "dark"],
    "checklist": [
      {"id": "hero", "text": "The headline fits without an awkward break"},
      {"id": "cta", "text": "The download button shows without scrolling"}
    ]
  }]
}
```

CLI:

```sh
tasks review check --card GITKITTIE-131 --title "Site onboarding, round 1" \
  --url https://preview-95.gitkittie.app/tasks/onboarding \
  --size phone --size desktop --size 1080x1920 \
  --item "The headline fits without an awkward break" \
  --item "The download button shows without scrolling" \
  --for sil --on-accept testing --on-changes in-progress
# --request <id> adds the check to an existing request; checklist ids come from the text.
```

Reading results: `list_reviews` returns each check with `status`, `results` as stored, and a
`failed` list for convenience:

```json
"failed": [{"size": "phone.light", "item": "cta", "text": "The download button shows without scrolling",
            "note": "Below the fold; the cookie bar pushes it down.", "screenshot": "results/onboarding-page-phone.light.png"}]
```

A new tool `get_review_file` (`tasks review file <request> <path> [-o <file>]`) returns a file of a
request (a screenshot) as base64, so an agent without a clone of the board can look at it. A redo
is a new check with `revises: <old id>`, then `handle_review_item` on the old one, as for files.

## 4. Assigning reviews to people

### 4.1 Schema

```yaml
for: [sil]            # board user ids; a single id is allowed (for: sil)
```

Written by the agent (or by whoever creates the request). Absent or empty: everyone. The key is
`for` and not `assignee`: on a card `assignee` is one id and means "who does the work"; here it is
who decides, and it can be several people.

### 4.2 Who decides

With several people, **any one of them** decides an entry, as today (`decided_by` says who)
*(question `several`)*. "Everyone must approve" needs a decision per person per entry
(`decisions: [{by, status, at}]`), and it changes outcome, push and the screens. That's a later
step, if it turns out to be needed.

### 4.3 Who sees it

*(Question `visibility`.)* Recommended:

- A request `for` other people is left out of your Reviews list, the inbox across boards
  (`AppModel+ReviewInbox`), the badge, the waiting counts and local notifications.
- A **For me / Everyone** filter in the Reviews list (Mac: the list's filter menu; iPhone: the
  list's ⋯ menu), *For me* by default, remembered per device. *For me* includes unassigned
  requests. Anyone can switch it: there are no board roles, and roles would be new contract for
  little gain.
- Someone else's request opened through *Everyone* is **read-only** with a line on top: "For
  Herma. You can comment." Comments are allowed, decisions and checklist answers are not.
- The card's review badge counts only what's for you.

**This is routing, not privacy.** The request is a file in a repository everyone on the board can
read. The spec and the guide say so; anything secret doesn't belong in a review.

### 4.4 Who you are

The app already maps the signed-in account to a board user (`AppModel.reviewerID(among:)`: the
provider login, the folder server's Tailscale login, or the Mac's user name, matched against each
user's `github` or `id`). Two gaps:

- **No match** *(question `identity`)*: recommended, ask once per board: "Which one are you on
  GitKittie?" with the board's `kind: human` users, plus "None of these" (you then see
  unassigned requests only and decide as your login). Stored per device and board, and changeable
  in the board's settings. Not written to the board README by itself: that's a shared file.
- **Show it:** the Reviews header shows "Reviewing as Sil", so a wrong mapping is visible.

### 4.5 Notifications

- **Local** (background refresh, the Mac's timer): only requests for you, or unassigned.
- **Push** (GITKITTIE-128's relay): when a device registers, the relay already checks the user's
  token against the repository; it also records that token's login. At alert time it reads the
  board's effective `users` (root `README.md` and the board's `README.md`, as the GitHub App) and
  maps `for` ids to logins through `github:`. An alert goes to devices whose login is one of them;
  an unassigned request goes to all. A `for` id with no `github` reaches nobody by push; the app
  still shows it.
- **New for you counts as new:** `waitingEntries` becomes per user, so changing `for` from Herma to
  Sil announces the request to Sil even though nothing new was added.
- `notify` keeps its meaning (how loud). `for` says who.

### 4.6 Agents

- `create_review` gains `for` (ids validated against the board's effective `users`; unknown ids
  refused with the list). The guide: put the request on the person who asked for the work when the
  card says who that is; leave it unassigned otherwise.
- `list_reviews` gains a `for` filter and returns `for` on each request.
- An agent can be in `for` too (an agent reviewing another agent's work). Out of scope for the
  first release's screens; the file allows it.

## 6. The full `review.md` schema

Every new key is optional. A file without them reads and behaves exactly as today. Writers keep
unknown keys (both writers already go through Yams' ordered `Node` / the TS frontmatter round

    decided_at: null

### Who writes which fields (additions)

| Field | Written by |
|---|---|
| `for`, `due`, `on_accept` / `on_changes` / `on_reject` (request, items, checks) | the agent |
| on checks: `id`, `url`, `title`, `note`, `sizes`, `appearance`, `checklist`, `revises` | the agent |
| on checks: `status`, `decided_by`, `decided_at`, `results` | the app (reviewer) |
| `results/` files in the request folder | the app (reviewer) |
| `actions_run` | the app (reviewer), append-only; only `undone_at` is ever set later |
| `comments` on checks | both, append-only |
| `handled_at` on checks | the agent |

### Compatibility

- Old apps ignore `checks`, `for`, `due`, `on_*` and `actions_run` and keep them when they write
  (both writers round-trip the whole mapping). An old app shows the request without its checks,
  to everyone, and runs no actions.
- **Risk:** an old `handle_review_item` that finds nothing pending removes the request folder, and
  it doesn't count checks. All agent writes go through the Tasks app (MCP and CLI), so the guard
  is: update `AgentReviews` cleanup and the relay's `waitingEntries` to count checks in the first
  card, before any agent can create a check. `create_review` on an old app version would drop the
  `checks` field, so the guide only documents checks once the app supports them.
- The relay (GITKITTIE-128) parses with `gitkanban-core`, so checks and `for` reach it with the
  parser change.

## 9. Decisions asked in the review

|---|---|---|---|
| `when` | When do request actions run? | Automatically on the deciding decision, with Undo | "Finish Review" button: one more step, a summary of what will happen first |
| `outcome` | Mixed decisions | changes > reject > accept | "Rejected doesn't block accept": rejected = dropped, the card can still pass |
| `review-fields` | Fill the card's `reviewer` / `review_outcome`? | Yes | Move only |
